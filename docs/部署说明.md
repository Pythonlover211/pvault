# pvault 部署说明（GitHub Pages）

> **发布前必读：当前实现分支是 `feat/ledger`，不是 `main`。**
> 方案 A 的 workflow 只在 **push 到 `main`** 时触发，方案 B 也只发布你在第 4 步选定的那个分支，
> 所以**必须先把 `feat/ledger` 合并进 `main` 再 push**，否则线上跑的还是旧的（甚至空的）代码：
>
> ```bash
> git checkout main
> git merge feat/ledger
> git push -u origin main
> ```
>
> 下面的步骤都假定你站在**要发布的那个分支**（下面按惯例写 `main`）上。

## 为什么能这样部署

pvault 是纯静态站点：没有构建步骤、没有依赖、没有服务端接口。仓库根目录下的
`index.html` 就是入口，`app/`、`styles/`、`icons/` 是它引用的全部资源。
把这些文件当静态文件发出去就够用，不需要打包。

但「从哪里发」有两种选择，差别在于**会公开哪些文件**：

| | **方案 A：用 Actions 发布**（推荐） | **方案 B：从分支根目录发布** |
| --- | --- | --- |
| 公开的内容 | 只有运行时需要的 32 个文件 | 仓库根目录下的**一切**：`docs/`、`tests/`、`scripts/`、`package.json`、`.gitignore` … |
| 构建 | **零构建**（只 `cp` 文件，不装依赖、不打包） | 零配置 |
| 需要什么 | 仓库里放一个 `.github/workflows/deploy.yml` | 在 Pages 设置里选分支和目录 |
| 代价 | 无 | `docs/superpowers/plans/*.md` 里有相当详细的安全设计，会被任何人读到 |

**选方案 A。** 账目数据两种方案下都不会泄露（这个 app 没有任何上传接口，见下文
「托管的是代码，不是数据」），但**设计文档与测试代码不该公开**。

## 方案 A：用 Actions 发布（推荐，只公开运行时文件）

仓库里已有 `.github/workflows/deploy.yml`：checkout → 把运行时文件拷进 `_site` → 上传并发布。
它只做一件事——决定**哪些文件进站点**，用白名单：

```bash
mkdir -p _site
cp index.html manifest.webmanifest sw.js .nojekyll _site/
cp -r app styles icons _site/
```

不在这个名单里的东西永远不会进 `_site`，也就永远上不了网。workflow 里随后还有一步断言：
如果 `_site` 里出现了 `docs`、`tests`、`scripts`、`.git`、`package.json` 中任何一个，直接失败
（并把 `find _site -type f | sort` 的完整清单打进 Actions 日志，便于人工确认）。

**这仍然是零构建**，不要被「CI」两个字吓到：workflow 里只有 `mkdir` / `cp` / `find`，
不 `npm install`（仓库本来也没有依赖）、不打包、不压缩、不碰一行代码。
前端代码本身依旧无构建——`index.html` 里那句 `<script type="module" src="./app/main.js">`
就是把源码直接喂给浏览器。这个 workflow 存在的唯一理由是「拷哪些文件」，不是「怎么构建」。

### 这份白名单是怎么核对出来的

运行时文件集合不是凭记忆写的，是拿 `sw.js` 的 `ASSETS` 清单和 `index.html` 的引用反查出来的：

- `sw.js` 的 `ASSETS` 有 **31 条**，它就是这个 app 运行时资源的权威清单
  （`cache.addAll()` 是原子的，清单里只要有一条 404，整个 install 就失败、离线能力归零）。
  去掉重复项（`./` 与 `./index.html` 指向同一份文件）后是 30 个文件：
  根目录的 `index.html`、`manifest.webmanifest`，加 `styles/`（3 个）、`icons/`（1 个）、`app/`（24 个）。
- `sw.js` **自己**不在 `ASSETS` 里，但必须发布：`app/main.js` 里用
  `navigator.serviceWorker.register('./sw.js')` 注册它，而且它必须待在站点根目录，
  `scope` 才能覆盖整个 `/pvault/`（这也决定了它不能被挪进 `app/`）。
- `.nojekyll` 必须发布，理由见第 4 步下面那段。在方案 A 下它是从仓库根目录被**拷进 `_site`** 才生效的。
- 反过来，`package.json`、`.gitignore`、`docs/`、`tests/`、`scripts/` 都不是运行时资源。

结果：`_site` 里正好 **32 个文件** = 30（`ASSETS` 对应的文件）+ `sw.js` + `.nojekyll`。
覆盖了 `index.html` 引用的全部 6 个资源、`manifest.webmanifest` 里的图标与 `start_url`、
以及 `ASSETS` 的全部 31 条路径，没有任何多余文件。

## 方案 B：从分支根目录发布（会把 docs/ tests/ scripts/ 公开）

就是「Pages 设置里选分支 + `/ (root)`」那种最省事的做法。配置最简单，但代价必须写清楚：

**Pages 从分支发布不带白名单**，仓库根目录下的一切都会出现在
`https://<你的用户名>.github.io/pvault/` 上，任何人（含搜索引擎）都能读：

- `docs/`：设计规格、实现计划、手动验证清单、本文件。其中
  `docs/superpowers/plans/2026-09-23-pvault-ledger.md` 有**相当详细的安全设计**
  （数据模型、IndexedDB 结构、隐私边界），属于不该公开的东西。
- `tests/`：全部单测源码。
- `scripts/dev-server.js`：本地开发服务器（它内部那份路径白名单只保护局域网里的开发服务器，
  对 Pages 完全无效）。
- `package.json`、`.gitignore` 等仓库文件。

**账目本身仍然安全**：这个 app 没有任何上传接口，账目只存在手机的 IndexedDB 里
（见下文「托管的是代码，不是数据」）。泄露的是**代码与设计文档**，不是你的账。
只有在你不介意这些内容被读到、或只是临时验证时才用方案 B；长期使用请改回方案 A
（切回方法：把 Pages 的 Source 改回 `GitHub Actions` 即可，不需要动代码）。

## 完整流程

### 1. 在 GitHub 新建仓库 `pvault`

- 权限选 **Public**（Pages 的免费额度只对公开仓库开放；私有仓库的 Pages 需要付费计划）
- **不要**勾选 "Add a README / .gitignore / license"：本地已经有提交历史，勾了会多出一个
  与本地无关的初始提交，`git push` 会因历史分叉被拒

### 2. 关联远程仓库

```bash
cd pvault
git remote add origin https://github.com/Pythonlover211/pvault.git
# 若之前加过（remote 已存在）：git remote set-url origin https://github.com/Pythonlover211/pvault.git
```

### 3. 推送

```bash
git push -u origin main
```

`-u` 记下上游分支，之后直接 `git push` 就行。
（如果本地默认分支叫 `master`，要么改推送目标 `git push -u origin master:main`，
要么先本地改名 `git branch -M main`。）

### 4. 打开 Pages

仓库 → **Settings** → 左侧 **Pages**：

- **方案 A（推荐）**：**Source** 选 **`GitHub Actions`**
  —— 不必再选分支和目录，发布交给仓库里的 `.github/workflows/deploy.yml`。
  它只在 push 到 `main` 时自动触发；首次也可以在仓库 **Actions** 页面选中
  `Deploy to GitHub Pages` 点 **Run workflow** 手动跑一次（workflow 里带了 `workflow_dispatch`）。
- **方案 B**：**Source** 选 `Deploy from a branch`，**Branch** 选 `main`，**目录**选 `/ (root)`。

最后点 **Save**。

> 顺序上先设 Source、再 push 最省事。如果第 3 步的 push 抢在前面触发了一次 workflow，
> 那时 Pages 还没启用、`deploy-pages` 会失败（报的是 Pages site 没配置之类，**不是代码问题**）。
> 把 Source 改成 `GitHub Actions` 之后，到 **Actions** 页面点 **Re-run all jobs**（或 Run workflow）
> 重跑一次就成了。

> `.nojekyll`（空文件）是必须的：Pages 默认用 Jekyll 处理站点，
> 而 Jekyll 会**忽略所有下划线开头的文件/目录**。现在虽然还没有这类文件，
> 但一旦以后加了 `_headers`、`_redirects` 之类，没有 `.nojekyll` 它们会凭空消失，
> 而且不报任何错。空文件就够，不需要写内容。
> 方案 A 下它由 workflow 从仓库根目录拷进 `_site` 根目录；方案 B 下它本来就在分支根目录。

### 5. 等 1~2 分钟，访问

```
https://pythonlover211.github.io/pvault/
```

首次发布要等一会儿（方案 A 看 **Actions** 页面里 `Deploy to GitHub Pages` 这个 workflow 的状态，
它会打印出 `_site` 的文件清单；方案 B 看 `pages build and deployment`）。
看到记账首页、能记一笔就算成功。

注意地址里**带 `/pvault/` 这层子路径**。项目里所有引用都写成 `./` 开头的相对路径
（`./styles/base.css`、`./sw.js`），所以它在子路径下能正常工作；如果你以后改成绑自定义域名
（根路径发布），相对路径同样成立，不用改代码。

### 6. 手机上装到桌面（PWA）

**用安卓版 Chrome 或 Edge** 打开上面的地址 → 右上角菜单 → **添加到主屏幕** / **安装应用**。

装好后点桌面图标应当是**全屏无地址栏**（`manifest.webmanifest` 里的 `display: standalone`）。
长按图标还会出现「记一笔」快捷方式，直接进录入面板。

### 7. 以后怎么更新

```bash
# 本地改完代码
git add <具体文件>
git commit -m "..."
git push
```

然后手机上刷新页面（或直接关掉重开）。方案 A 下 push 到 `main` 会自动触发一次部署
（Actions 里 `Deploy to GitHub Pages` 变绿），等它跑完再刷新；**如果没看到新内容，把 `sw.js` 顶部的
`CACHE` 版本号 +1（`pvault-v1` → `pvault-v2`）再推一次。**

这是本项目的头号坑，原因值得记住：

- 浏览器判断「Service Worker 有没有新版」，靠的是 `sw.js` **这个文件本身**的字节有没有变。
- `CACHE` 版本号不变时，`install` 里那句 `cache.addAll(ASSETS)` 仍然往**同一个**缓存里塞，
  而缓存优先策略会一直命中旧副本——你改了 `app/ui/ledger-home.js`，线上 `sw.js` 却没变，
  手机上永远显示旧界面，本地怎么测都是好的。
- 只改 `CACHE` 名字还不够保险：改完 `sw.js` 后，安卓 Chrome 要等**所有** pvault 页面都被关掉
  才会装新 SW。代码里已经用 `skipWaiting()` + `clients.claim()` 缩短了这个过程，
  但手机上「退到后台」不算关闭，必要时手动从最近任务里划掉再重开。

- [ ] `https://<你的用户名>.github.io/pvault/tests/` 同样应当 404

## 托管的是代码，不是数据

这一点必须说清楚，它决定了这个 app 的隐私边界：

- 线上托管的只有 **HTML / CSS / JS / 图标**这些「程序」。你的账目、账户、预算、固定支出、
  应收，全部存在**手机浏览器自己的 IndexedDB** 里（库名 `pvault`），**从不上传**。
- 整个项目**没有任何上传账目的网络接口**：代码里没有 `fetch`/`XMLHttpRequest` 往任何服务器
  POST 数据，也没有账号、没有登录、没有云端同步。
- 所以它**断网可用**：Service Worker 预缓存了全部资源，飞行模式下重新打开照样能记账、看统计
  （这正是 `docs/手动验证清单.md` 里要真机确认的那几条）。
- 反过来，数据也**不会**跟着你走：换手机、卸载浏览器、清空站点数据，账目就没了。
  同一台手机上「添加到主屏幕」的窗口和浏览器标签页共用同一份 IndexedDB，所以两边看到的是同一套数据。
- 清理的连带影响：在 Chrome 里「清除浏览数据」勾选了「Cookie 及网站数据」时，
  IndexedDB 会一起被清掉，`pvault` 库连同种子数据会被重建（分类 12 条、账户 5 条回来，交易全没了）。
- 仓库是 Public，但 **GitHub 上看不到你的任何一笔账**——账目从来没有离开过手机。
- 顺带一提，公开的也只是**程序**：方案 A 发布出去的 `_site` 只有 32 个文件
  （`index.html`、`manifest.webmanifest`、`sw.js`、`.nojekyll` + `app/`、`styles/`、`icons/`），
  `docs/`（含安全设计）、`tests/`、`scripts/` 都不在公开站点里。

## 已知风险与替代方案

- **华为自带浏览器**：对 PWA 的支持不完整，「添加到主屏幕」可能只是加个书签（有地址栏、
  没有离线），角标也不会出现。遇到这种情况改用**安卓版 Chrome / Edge**打开同一地址再添加。
- **iOS Safari**：可以「添加到主屏幕」并全屏，但**不支持 Badging API**（桌面角标不会出现，
  代码里已经做了静默跳过，不会报错），离线缓存策略由系统的 7 天未使用回收机制管理。
- **HTTP 部署不可用**：Service Worker 只在安全上下文里工作（HTTPS 或 localhost）。
  局域网 http 预览时 SW 不注册是正确的（`navigator.serviceWorker` 都没有），
  但这意味着**离线能力只能在 Pages（HTTPS）或 localhost 上验证**。
