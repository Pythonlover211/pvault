# pvault 手动验证清单

这份清单是留给人（在真实浏览器里）逐条勾选验证的。

为什么需要它：**IndexedDB 是浏览器 API，Node 里不存在**，所以 `app/db.js` 这一层的读写行为
无法用 `node --test` 自动覆盖（本项目的零依赖约束也排除了引入 fake-indexeddb 之类的 polyfill）。
可以自动测的部分已经放在 `tests/schema.test.js`：`app/schema.js` 的种子数据与仓库定义是纯函数，
没有任何浏览器全局引用，因此能在 Node 里直接 import 并断言。

验证环境：`npm run dev` → 浏览器打开 `http://localhost:8080` → 开发者工具。
每一步的勾选框都应当在**真机浏览器**里实际观察过后再打勾。

## 本次交付的验证状态

**先说结论：这份清单里所有条目的复选框目前都还是空的。** 计划 2（密码箱 + 备份）的 11 个功能任务
代码已完成并合入 `feat/vault`，但**没有任何一条界面或存储行为被自动测试或真机确认过** ——
下面这一节说明「什么已经由机器验证、什么必须由人验证」。

### 完全没有被自动测试覆盖的（必须由人工在真机上过一遍）

- **所有 IndexedDB 真实读写**：`db.js` / `store.js` / `vault-store.js` / `backup-store.js` 的落库、
  事务原子性、索引区间查询边界。本项目零依赖，不引 fake-indexeddb，Node 里也根本没有 IndexedDB。
- **加密保险库的端到端**：初始化 → 写条目 → 刷新 → 重新解锁 → 改主密码 → 用恢复码解锁这一整条链，
  以及空闲 5 分钟自动上锁。密钥链路的每一段在 Node 里单独测过，但「浏览器真的这么跑」没测过。
- **所有界面**：三个 Tab、各面板、密码箱三态、条目编辑、备份面板的真实渲染、排版、焦点、
  输入法与滚动锁。开发环境里没有浏览器，这些界面**从未被真正渲染过**。
- **剪贴板**：复制成功，以及 30 秒后自动清空（`navigator.clipboard` 需要权限与安全上下文）。
- **文件下载与文件选择**：导出 `.pvault` 真的下载下来、`<input type="file">` 真的唤起系统选择器。
- **Service Worker**：install / activate / fetch 三段、离线可用性、版本更新与自动刷新。
  目前只做过静态核对：`node --check sw.js`、ASSETS 逐条请求 200、ASSETS 与磁盘文件双向对齐。
- **PWA 安装**：添加到主屏幕、独立窗口、桌面图标角标、长按快捷方式。

因此下面每一条都必须在真机上人工勾选，尤其是「密码箱（数据层）」「备份与恢复」「密码箱（界面）」
「密码箱条目编辑」「备份与恢复（界面）」「PWA 与离线」几节 —— 计划 2 的全部交付都落在那里。

### 查询边界（`getByRange` 的上界开区间）

- [ ] 区间查询不包含上界那一瞬间：`getByRange('txns', 'by_occurredAt', 本月1日0点, 下月1日0点)`
      不返回 `occurredAt === 下月1日0点` 的交易
- [ ] 空区间（lower === upper）不抛错：`await db.getByRange('txns', 'by_occurredAt', t, t)` 返回 `[]`
      - 备注：现行 W3C IndexedDB 3.0 规范里 `IDBKeyRange.bound()` 只在 `lowerKey > upperKey` 时抛
        `DataError`，两边相等且上界开放时是空区间；但 MDN 的异常表仍写着「lower 与 upper 相同且任一
        边界开放 → DataError」，属于旧版描述。若这条在真机上抛错，说明需要给空区间加特判。

## 发票

对应 `app/ui/invoice-view.js`（列表、搜索、筛选、汇总）、`app/ui/invoice-editor.js`（新建 / 编辑 / 拍照选图）、

这 7 个文件里只有 `invoice-model.js` 与 `image-scale.js` 能进 Node（校验、查重键、标题、尺寸计算、
该不该压、体积预估），它们已经在 `tests/` 里被覆盖；**其余全是浏览器 API 的编排**——
`createImageBitmap`、`canvas`、`Blob`、IndexedDB、相机与文件选择器在 Node 里都不存在，
所以下面每一条都必须在真机上人工勾。

**本轮修过的坑，优先验这一条**：手机竖着拍的照片曾经会**躺倒**。`createImageBitmap` 在 Chromium 里
默认不套用 EXIF 方向（`'none'`），而重编码成 JPEG 会把 EXIF 一起丢掉——一旦这样存进去就再也正不回来；
更迷惑的是同一张图直接 `<img>` 显示时反而是正的，所以现象看着像偶发。现在显式传了
`imageOrientation: 'from-image'`，并且失败时退回 `<img>`（它本来就是 from-image）。这条只能用
**竖拍的原图**在真机上验。

**先确认自己看到的是新版**：本轮把 `sw.js` 的 `CACHE` 从 `pvault-v12` 升到了 `pvault-v13`，7 个新文件
也进了 `ASSETS` 预缓存清单。手机上如果「底部根本没有发票 Tab」，先怀疑旧 Service Worker 还在发旧缓存
（彻底关掉页面再打开，或卸载后重新添加到主屏）。

### OFD 文件

> **验证前必须先重新打包**：这一轮改过 `MainActivity.java`（导出落盘的 MIME），而 APK 里的网页资源是打包时从仓库复制的产物。直接用旧包验会把「导出打不开」误判成功能问题。先在仓库根跑一次 `scripts/build-apk.ps1` 再 `adb install -r`。

> **准备一个几 MB 的 OFD 样本**：PDF / OFD 不走压缩，导出时整份字节要变成 base64（约 ×1.33）整串穿过 JS 桥交给 Java 落盘——这是本功能新出现的最长路径（备份那条路早就在用同一机制，但闸门允许到 45 MB）。一两百 KB 的样本验不到它。

- [ ] 点「选图片 / PDF / OFD」能选到一个 `.ofd` 文件，选完面板不报错
- [ ] **这一条决定整个功能的成败**：确认 `.ofd` 在系统选择器里**真的能被选中**。安卓把 OFD 报成 `application/octet-stream`、或 WebView 忽略扩展名过滤，都会让它在选择器里被置灰——那时功能等于没做，而且是静默的（用户只会以为这个 App 不支持 OFD）。选不中的话把 accept 放宽（加 `application/octet-stream`，或干脆 `*/*`），但**必须同时加类型白名单**：`fileKind` 对不认识的一律返回 `'image'`，一放宽就会把 xlsx / docx 也收进来，以「图片未能压缩，已按原样保存」的姿态存进库，导出时还会被命名成 `.jpg`
