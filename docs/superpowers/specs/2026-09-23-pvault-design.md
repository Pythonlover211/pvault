# pvault · 记账 + 密码箱 设计规格

> 状态：待用户审查
> 日期：2026-09-23
> 项目目录：`E:\codex-project\pvault`
> 形态：PWA（网页 App，加到手机主屏幕）

---

## 0. 一句话

一个只跑在你自己手机浏览器里的记账 + 密码保管工具，**数据永远不离开手机**。

---

## 1. 要解决的问题

| # | 用户确认的痛点 | 对应设计 |
|---|---|---|
| 1 | 记一笔太繁琐 | 半屏录入面板 + 自建数字键盘 + 按时间/历史智能默认分类，**3 个动作内记完** |
| 2 | 现有工具看不清统计 | 环形占比（中心显示总额、可下钻）+ 分类明细 + 近 6 个月趋势 + 环比 ±% |
| 3 | 想要预算与提醒 | 三层预算（总额 / 分类 / 固定支出），首页进度条绿→黄→红 |
| 4 | 数据要自己掌控 | 纯本地 IndexedDB，无账号、无服务器、无任何上传接口 |
| 5 | 要一个统一加密箱 | 密码箱：网站账号 / 银行卡证件 / 零散备注，AES-GCM 加密 |

**用户原话（保留措辞）**

- 「我想要做一个自用的app」
- 「还要有一个记录密码的页面」
- 「账单导入，不限格式」
- 「到时候给我改到d盘去，不要占用c盘空间」
- 「尽量不要占用我c、e盘空间」

## 2. 明确不做（防止范围蔓延）

| 不做 | 原因 |
|---|---|
| 后台定时推送通知 | Web 推送必须过一台推送服务器，等于把账目托管出去，与「数据自己掌控」冲突 |
| 多用户 / 共享账本 | 自用；工作区已有 `accounting-miniprogram` 覆盖多人场景，本项目与它无关 |
| 多币种 | 无实际需求 |
| 云同步、账号登录 | 同上 |
| 指纹解锁 | V1 不做（见 11 节风险）；主密码解锁一次管 5 分钟，够用 |
| 打包 APK | V1 不做；真要做时一律装 D 盘（见 10.3） |
| 自动记账（读短信 / 通知） | 浏览器拿不到这些权限 |

## 3. 形态、部署与更新

- **形态**：网页 App（PWA）。手机浏览器打开 → 添加到主屏幕 → 点图标全屏使用。
- **目标设备**：用户的鸿蒙 4.3 手机（可装安卓版 Chrome / Edge）。华为自带浏览器对 PWA 独立窗口支持不完整，**首选安卓版 Chrome 或 Edge**。
- **部署**：GitHub Pages。推到 `github.com/Pythonlover211/pvault`，代码托管在云端。
- **关键区分**：**托管的是代码，不是数据**。app 没有任何上传账目的网络接口，断网可正常使用。
- **更新**：改代码 → `git push` → 手机上刷新即生效。数据不受影响。
- **离线**：Service Worker 缓存全部资源，首次加载后离线可用。

## 4. 技术选型与硬约束

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | **不用**，原生 HTML / CSS / ES Modules | 省空间、无构建、改完刷新即生效 |
| 构建 | **无** | 不需要 node_modules、不需要打包步骤 |
| 数据存储 | IndexedDB（手写薄封装） | 手机本地，容量足够，支持结构化数据 |
| 加密 | 浏览器内置 **WebCrypto** | 不引任何第三方密码学库——那是这类项目最常见的翻车点 |
| 图表 | **手写 SVG** | 零依赖、离线可用 |
| 测试 | Node 24 内置 `node:test` + `node:assert` | 零依赖，不装 vitest / jest / playwright |
| 部署 | GitHub Pages（静态） | 免费、不依赖电脑开机 |

**空间约束（用户明确要求）**

- 项目源码总量目标 **< 1 MB**，几十个文本文件
- 不产生 `node_modules` / `dist` / 打包缓存
- 手机端数据存在手机，不占电脑盘
- 将来若打包 APK：`ANDROID_HOME=D:\Android\sdk`、`GRADLE_USER_HOME=D:\gradle`、Android Studio 与构建产物全部指向 D 盘，装完须实际核查 C 盘未被创建 `.gradle` 与 `AppData\Local\Android`

## 5. 界面结构

底部三个 Tab：**记账 / 统计 / 密码箱**。

> 「本月花了多少」和「为什么花这么多」是两个不同的问题，分开放，避免一个页面互相打架。

### 5.1 记账（首页）

从上到下四块：

1. **月份 + 隐藏金额的小眼睛** —— 在别人面前打开不尴尬
2. **本月支出大数字**，下面一行带收入与结余
3. **预算进度条** —— 绿→黄→红三段变色，附「还剩多少 / 日均可用多少」（日均可用 = 剩余预算 ÷ 本月剩余天数）
4. **今天的流水** —— 每条标注所属账户，方便核对刚记的账

另外：一行「应收 ¥245」的小字（不占地方，点进去展开明细）。

**桌面图标角标**显示一个数字：临近的信用卡还款笔数 + 今天该记的固定支出笔数；没有待办时不显示角标。

右下角**悬浮 + 按钮** → 点开是**从底部滑出的半屏录入面板**（上半屏仍能看到今天的流水，不是把首页整个盖住）。

### 5.2 录入面板

- 顶部：支出 / 收入 / **转账** 三态切换
- **金额**：大字显示，配**自建数字键盘**（不弹系统键盘：更快、不遮挡）
- **分类九宫格**：按当前时间与历史自动高亮最可能的分类（中午→餐饮，傍晚→交通），想改点一下
- **账户**：默认上次使用的那个
- **时间**：默认现在，右上角可改
- **备注**：可选
- **有人分摊**：勾选后填对方与金额
- **完成**：记完面板收起、回到首页、**3 秒内可撤销**

**附带加速**：PWA 长按桌面图标 → 快捷方式「记一笔」直达录入面板（安卓 shortcuts）。

### 5.3 统计

- 月份切换 + **与上月环比（±%）**
- **环形占比图**：圆心显示本月总额；图例每项带金额与百分比；**点色块下钻到该类明细**
- 下方附**分类明细列表**（金额降序，带占比条）
- **近 6 个月趋势**柱状图
- 超支分类**标红并置顶**
- 应收 / 应付汇总

### 5.4 密码箱（已实现）

实现：`app/ui/vault-view.js`（三态与列表/详情）、`app/ui/vault-editor.js`（条目编辑）、`app/ui/clipboard.js`。
视图本身不记「我上锁了没」，每次渲染前问一次仓库层（`isInitialized()` / `isUnlocked()`），因此空闲上锁后界面一定会切回锁屏。

**三个状态**

1. **未初始化 —— 初始化引导**：说明「忘记主密码没有任何找回方式，但有恢复码 → 抄下来离线保存」→ 设置主密码（输入两次，至少 8 位，不足 8 位或两次不一致时创建按钮禁用）→ 创建成功即进入下面的恢复码展示页。
   - **恢复码展示页（这一屏不允许跳过）**：恢复码按 8 组 4 字符等宽显示，可选中、可一键复制；**必须先勾选「我已抄写并妥善保存这串恢复码」，「进入密码箱」按钮才可点**。这一屏没有任何返回或关闭入口，因为**这是用户唯一一次能看到恢复码的机会**（`initVault` 不把它写进任何可再读的地方）。
2. **未解锁 —— 锁屏**：主密码输入 + 解锁按钮，下方一个可折叠的「用恢复码解锁」入口（两条路独立）。
   - **连续输错 3 次之后，此后每次尝试前都先等 1 秒**（按钮显示「请稍候…」并禁用），成功一次即清零。这一秒的作用是让人工逐个试密码变慢、并给「是不是记错了」留出停顿；真正的防线仍是 PBKDF2 的 600,000 轮。
   - **用恢复码解锁成功后，页面顶部常驻一条提醒**「你正在用恢复码访问，建议尽快修改主密码」。它跨渲染保持（切进详情、上锁再解锁都在），直到用主密码成功解锁或刷新页面。
3. **已解锁 —— 列表 + 详情**：
   - 顶部搜索框 + 右上「＋ 新建」；搜索匹配标题与全部字段值（忽略大小写），输入时只重画列表区，不重建搜索框（否则正在拼的中文会丢）。
   - 条目按**三个分组**显示（网站与 App / 银行卡与证件 / 零散备注），每组标题带数量，**空分组不显示**；无匹配时显示空态。
   - **详情**：字段按类型定义顺序逐个列出，空字段不列；`password` 与 `cvv` **默认打码**（`maskSecret`），旁边是「显示 / 隐藏」切换；每个字段带「复制」。**明文从不进 DOM**——掩码态与明文态都只写文本节点，隐藏时 DOM 里根本没有明文（不做「值在 `value` 里、只显示成圆点」那种看源码就能读到的假遮罩）。
   - 底部「锁定」与「修改主密码」两个入口。
- **复制后 30 秒自动清空剪贴板**：清空前先读一次剪贴板，**只有内容仍是自己刚写进去的那串时才清**；读不到（权限/不支持）就什么都不做——宁可不清理，也不能误清用户后来复制的东西。

## 6. 数据模型

**所有金额一律以「分」为单位的整数存储**，禁止浮点数参与金额运算。

```
Account         账户
  id, name, kind(cash|savings|credit), icon,
  trackBalance(bool), balanceCents(可空),
  billDay(信用卡账单日), dueDay(信用卡还款日),
  archived, sort

Category        分类
  id, name, icon(emoji), kind(expense|income), sort, pinned

Transaction     交易
  id, kind(expense|income|transfer),
  amountCents, categoryId, accountId, toAccountId(转账目标),
  occurredAt, note, source(manual|import), recurringId,
  createdAt, updatedAt

Share           分摊（一笔交易的他人份额）
  id, txnId, personName, amountCents, settled, settledAt

Receivable      借还
  id, personName, direction(owedToMe|iOwe),
  amountCents, occurredAt, dueAt, settledAt, note, sourceTxnId

Budget          预算
  monthlyTotalCents
  perCategory: { categoryId: cents }

Recurring       固定支出
  id, name, amountCents, categoryId, accountId,
  dayOfMonth, enabled, lastPromptedAt

Vault           加密保险库（存密文）
  version, kdf{ name:'PBKDF2-SHA256', iterations:600000 },
  saltPassword, saltRecovery,
  wrappedDekByPassword{ iv, ct }, wrappedDekByRecovery{ iv, ct },
  ciphertext{ iv, ct }, updatedAt

VaultItem       保险库条目（解密后）
  id, type(login|card|note), title, fields{}, createdAt, updatedAt
    login: username, password, url, note
    card : 卡号, 有效期, CVV, 发卡行, 备注
    note : 标题 + 正文

Settings        设置（明文）
  hideAmounts, lastBackupAt, backupReminderDays（暂无设置界面，默认 14）
```

**字段名以 `app/schema.js` 与各仓库层的实际落盘为准**（上面 `Vault` 一段即实现形状）：主密码与恢复码各有**独立 salt**、KDF 参数只记 `name`/`iterations`，`iv` 与 `ct` 收在各自的 `{ iv, ct }` 对象里（`wrappedDekBy*`、`ciphertext`），没有顶层 `iv`，也没有 `schemaVersion`。

**密码箱空闲上锁固定 5 分钟，不是配置项**：`Settings` 里曾计划过 `lockTimeoutMin`，实现时有记录地做成了固定值（理由见第 7 节），故不列在设置项里。

**分类与账户都可自定义**：增、删、改名、换 emoji 图标、排序。删除时若已有历史交易，改为**归档**而非真删，避免历史统计断裂。

### 6.1 三条关键规则

1. **交易分三种**：支出 / 收入 / **转账**。转账在录入时单独成一类（有自己的「从 → 到」账户选择），但在**统计口径里计入支出**——用户 2026-09-23 实测后要求「转账也要算到支出里面」。在分类占比里，所有转账统一归到一个内置的「转账」分类（`__transfer__`，图标 ⇄），这样分类各项之和仍然等于支出总额。
   **注意**：因为转账也计入支出，信用卡还款（银行卡 → 信用卡）会被算成消费。若将来觉得这笔重复了，再考虑加开关。
2. **储蓄类账户默认只当标签**（微信花了多少、银行卡花了多少），**不强制追踪余额**：现实里漏记一笔余额就对不上，天天对账会把人逼疯。想追真实余额可单独开启，并提供「校准」——以实际余额为准，差额记一笔调整。**信用卡才追踪欠款**，因为要提醒还款。
3. **借出去的和垫付的钱都不算消费**，记成「应收」；对方还回来时也不算收入。记账时勾「有人分摊」→ 填对方与金额 → 自动生成应收，自己的实际支出自动变成差额。

**实现状态（V1）**：账户余额追踪与「校准」**本版未实现**。`trackBalance` 字段保留在数据模型里（信用卡种子值为 `true`），但账户编辑界面不提供开关——避免给出一个勾了却没有效果的选项。余额展示与校准留待后续版本。

## 7. 密码箱的加密方案（已实现）

> 这是整个 app 里唯一「做错了没法补救」的部分。
> 实现：`app/crypto.js`、`app/recovery-code.js`（两个纯模块，有单测）、`app/vault-store.js`（依赖 IndexedDB 与 WebCrypto，靠手动清单验证）。全程用浏览器内置 WebCrypto，**不引任何第三方密码学库**。

- **信封加密**：随机生成 32 字节数据密钥 **DEK**（AES-GCM 256），用它加密整个保险库。
- **KEK** 由主密码经 **PBKDF2-SHA256（600,000 次迭代，16 字节随机 salt）** 派生，用 KEK 包裹 DEK 存入 `wrappedDekByPassword`。
- **恢复码（与本节初版描述的偏离，已确认）**：初始化时生成 **20 字节（160 位熵）** 随机值 → **Crockford Base32 → 32 个字符**，显示为 8 组 4 字符（初版写的是「32 字节 → Base32 → 52 个字符」）。改短的理由：160 位熵对「离线暴力破解不可行」已经绰绰有余，而 52 个字符被用户抄错的概率显著更高——**抄错一个字符就等于丢了恢复码**，这是真实风险。字母表用 Crockford Base32（去掉易混的 `I L O U`），解码时把 `I`/`L` 归一成 `1`、`O` 归一成 `0`，并忽略大小写、空格与连字符。DEK 再用恢复码派生的 KEK 包裹一份存入 `wrappedDekByRecovery`。**两条路都能开锁。**
- **改主密码**：只重新包裹 DEK（换 `saltPassword` 与 `wrappedDekByPassword`），**不重新加密任何条目**；`saltRecovery` / `wrappedDekByRecovery` 原样保留，因此**恢复码保持不变**，旧主密码立即失效。
- **重新生成恢复码（可随时补发，旧码立即失效）**：列表页有「重新生成恢复码」入口——输入主密码验明身份后，生成**新恢复码**与**新 `saltRecovery`**，用新码派生的 KEK 重新包裹**同一个 DEK**；`ciphertext`、`wrappedDekByPassword`、`saltPassword` 原样保留，所以**主密码不变、条目一条不动**（与改主密码同构：只换包裹 DEK 的那把钥匙，代价是一次 PBKDF2 而不是整库重加密）。**旧恢复码从这一刻起立即失效**，这是预期行为：换恢复码的意义就在于旧的那串从此没用，否则等于凭空多留一把没人数得清的钥匙。新码仍然只展示一次，走的是与初始化时**同一套**「抄写 + 勾选确认才能继续」的展示页（不另写一套）。**这是「恢复码只展示一次」的补救路径**：恢复码只在初始化那一屏出现过一次，用户手滑切了 Tab、在那一屏刷新了页面、或把抄好的纸条弄丢了，就再也没有地方能拿到它——而这三件事都不该是终局，手里还有主密码的人本来就完全有权补发一串。没有这个入口，「只展示一次」就是一条**不可逆**的风险。
- **密钥只活在内存里（与本节初版描述的偏离，已确认）**：DEK 只存在 `vault-store.js` 的模块级会话变量（`session`）里，**从不上盘**——磁盘上永远只有「被 KEK 包裹过的 DEK」与条目密文。上锁条件是**空闲 5 分钟**（初版写「切走超过 5 分钟」），**固定值、不是配置项**（初版 `Settings` 里的 `lockTimeoutMin` 未实现）：任何一次需要 DEK 的操作都会刷新计时，由一个 30 秒的定时器兜底检查，超时就清掉会话并广播上锁事件。理由是 PWA 里「切走」没有一个可靠的捕获点（`visibilitychange` 在手机上表现不一致）。语义不变：5 分钟没碰过密码箱就重新上锁；关闭页面同样清空（会话本来就不落盘）。
- **落盘形状**：整个保险库记录（版本、KDF 参数、两份包裹的 DEK、条目密文、更新时间）以**密文**形式存在 `settings` 表的 **`vault`** 键下；`vault` 为空表示「还没初始化」，与「已初始化但条目是空数组」在存储层面长得完全不一样，不会互相混淆。
- **指纹解锁不做**（V1）：WebAuthn 的 PRF 扩展在各家安卓浏览器（尤其中文 ROM 自带浏览器）支持参差，投入产出比低。

**忘记主密码的后果（必须让用户明确知道）**：没有任何找回方式——没有邮箱、没有客服、没有后门。恢复码是唯一退路；**恢复码丢失 + 主密码忘记 = 保险库永久打不开**，任何人都救不了。两件事要分清：**主密码丢了**没有救；**恢复码丢了**只要还记得主密码就还有救（列表页可随时补发新码，见上一节）。这两条会写在初始化界面和规格里，不藏在文档深处。

**记账数据不上锁**（用户选择）：明文存 IndexedDB，保证「掏出来就能记」。理由是记账数据位于手机浏览器沙箱内，其他 app 读不到；上锁会让每次记账多一步，与第一痛点直接冲突。

## 8. 备份与恢复（已实现）

实现：`app/backup.js`（纯模块，有单测）、`app/backup-store.js`、`app/ui/backup-view.js`。

- **导出一个文件**，记账数据与密码箱**装在一起**，整体 AES-GCM 加密。**导出时输入一次备份密码**（可以和主密码相同，也可以不同；两次输入一致且至少 8 位才允许导出）。文件名形如 `pvault-backup-2026-09-23.pvault`。
- **备份文件格式**：加密 JSON——`{ format: 'pvault-backup-encrypted', version, kdf: { name, iterations, salt }, iv, ct }`，扩展名固定 **`.pvault`**。每次导出都**新生成随机 salt**（复用 salt 会让同一个密码在任何时候导出的文件共用一把密钥）；解密一律以**文件里记的** `kdf.salt` / `kdf.iterations` 为准，这样迭代次数将来调高，老备份仍能用当初的轮数解开。
- **恢复流程**：装好 app → 选备份文件 → 输密码 → **先解密出摘要**（备份时间、交易 / 账户 / 分类条数、是否含密码箱）给用户看 → 用户点「确认覆盖并恢复」**之后才用一个事务覆盖全部数据**。摘要在确认之前**一次写入都没有**；覆盖清空与写入收在同一个事务里（`db.replaceAll`），绝不会留下「旧数据已清、新数据没写进去」的空库。导入完成后页面自动重新加载。
- **导入时的两条本地状态**：
  - `lastBackupAt` 保留**本设备当前的值**（从未有则用导入时刻），而不是照搬备份文件里的旧日期——否则刚导入完的人会看到「30 天前备份过」甚至「从未备份」这种假信息。
  - **备份里没有密码箱时，设备上已有的密码箱不清掉**（原样写回）：备份文件里根本没有它的替补，清掉就等于顺手毁掉用户设备上唯一一份密码箱密文。
- **备份提醒**：首页常驻一行小字显示上次备份是几天前，**超过 14 天（`backupReminderDays`）变黄**；从未备份时也显示并同样是警示色。数据只存手机一处，不提醒迟早会忘。

## 9. 账单导入

用户要求「不限格式」。纯本地无服务器，只能靠**为每种来源写的解析规则**，因此方案定为「**预设解析器 + 手动列映射**」：

1. **预设解析器**：内置微信支付账单、支付宝账单的官方导出格式（含 GBK 编码识别，用 `TextDecoder('gbk')` 回退）。
2. **通用列映射**：任意 CSV 首次导入时，预览前 5 行 → 手动指定哪列是**金额 / 时间 / 商户 / 收支方向 / 分类** → 保存成一个具名「格式配置」（如「招行 2026」）→ 下次同格式一键导入。
3. **去重**：按「时间 + 金额 + 商户」生成指纹，导入时提示「N 条重复已跳过」。
4. **先预览再落库**：解析后展示待导入列表，可勾选、可改分类，确认后才写入。

**范围说明**：V1 只支持 **CSV**。`.xlsx` 需要解压 + 解析 XML，与「零依赖」冲突，请先在 Excel / WPS 里另存为 CSV。这一条写在导入界面上，不让用户自己猜。

## 10. 错误处理与边界

| 场景 | 行为 |
|---|---|
| IndexedDB 被清空（浏览器清理数据） | 首页显示空状态，引导「导入备份」 |
| 存储配额不足 | 明确提示，并建议先导出备份 |
| 导入解析失败 | 指明具体原因：编码 / 列不匹配 / 金额格式非法 |
| 主密码输错 | 明确提示；连续输错 3 次之后，此后每次尝试前固定延迟 1 秒（见 5.4） |
| 主密码与恢复码都丢失 | UI 明确警告数据不可恢复（写在第 7 节） |
| 金额输入非法 | 输入层拦截；金额一律整数分 |
| Service Worker 有新版本 | 由 `controllerchange` 触发一次自动刷新（**仅在页面原本已被旧 SW 控制时**，首次安装不刷新）。数据全部在 IndexedDB，没有易失的页面状态，因此自动刷新比让用户手动点更省事 |
| 转账未选目标账户 | 禁止提交，指出缺什么 |

## 11. 测试策略

- **纯逻辑单元测试**（`node:test`，零依赖）：金额格式化与整数分运算、预算汇总、分摊计算、应收余额、颜色阈值（80% / 100%）、CSV 解析与列映射、去重指纹、**加密解密往返**、恢复码 Base32 编解码、日期与月度边界工具。
- **加密逻辑可在 Node 中直接测**：Node 24 提供 `globalThis.crypto`（WebCrypto），与浏览器同一套 API。
- **不引入任何测试框架或浏览器自动化工具**（省空间约束）。
- **DOM / 交互部分**：写成 `docs/手动验证清单.md`，逐条人工过（录入、撤销、下钻、锁定超时、导入、备份恢复、离线）。
