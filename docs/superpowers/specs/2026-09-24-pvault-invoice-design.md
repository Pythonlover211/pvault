> 状态：待用户审查
> 日期：2026-09-24

> 形态：PWA + 本地打包 APK（两条分发路径并存）

## 0. 一句话

把发票拍下来存进 App，标清楚哪张三张票对应哪笔账、哪些还没报销，**报销到账时顺手记一笔收入**。

---

## 1. 要解决的问题

用户在澄清阶段**四样全选**，本设计的每一节都对应其中之一：

| # | 用户确认的目的 | 对应设计 |
|---|---|---|
| 1 | 报销追踪 | 报销单（多张票打包）+ 三态进度 + 到账自动入账（第 6 节） |
| 2 | 存档备查 | 拍照/选文件存进 App，原图 + 缩略图分表存放（第 4 节） |
| 3 | 与记账挂钩 | 挂靠可选、多张票挂一笔账；记账侧可见「这笔有 N 张票」（第 5 节） |
| 4 | 记账凭证 / 报税 | 标准字段：号码、开票日期、金额、销售方、类型、抬头、税号、税额（第 3 节） |

**澄清阶段的其余决定（逐条来自用户选择）**

| 问题 | 用户的选择 |
|---|---|
| 发票本体存不存 | **图片/PDF 一起存** |
| 发票与账目的关系 | **多张票挂一笔账，挂靠可选** |
| 报销追踪深度 | **状态 + 报销单 + 到账自动入账** |
| 发票字段 | **标准**（不含发票代码/校验码/税率/开票人） |
| 入口位置 | **底部新增第 4 个 Tab「发票」** |
| 实施切法 | **拆两个计划，连着做** |

**用户原话（保留措辞）**

- 「可以加一个管理发票的功能吗」

**由我按默认定下、待用户审查时确认的三处**

| 项 | 默认 | 理由 |
|---|---|---|
| 报销单标题 | 自动生成「9月报销 · 3 张」，**可编辑** | 手填每次都要想名字；自动生成后大多数情况不用改 |
| 新建发票的报销状态 | 默认「待报销」，另给「**仅存档**」标记 | 有些票纯粹留底（保修、退换货），不该混进待报销统计里烦人 |
| 备份是否提供「不含图片」选项 | **提供** | 100 张发票的含图备份约 20~40 MB，手机上解析这么大的 JSON 有真实风险；只备数据要小两个数量级 |

## 2. 明确不做（防止范围蔓延）

| 不做 | 原因 |
|---|---|
| OCR 自动识别发票 | 纯前端零依赖做不到可靠识别；错一个字反而要人核对，比手输更慢 |
| 发票真伪查验 | 需要联网调用税务接口，与「数据不离开手机」冲突 |
| 发票代码 / 校验码 / 税率 / 开票人 | 用户选了「标准」档，这四项他明确没要 |
| 报销审批流（多人、多级） | 自用，只有「我提交、公司打钱」这一条线 |
| 一张票拆到多笔账 | 实际不存在；发票金额是固定的，拆账是记账那边的事 |
| 发票导出成 PDF / 打印 | 需要排版引擎，V1 不做；要留底就导出备份或从详情页存原图 |
| 自动读取相册里已有的发票 | 需要相册权限与遍历，收益不抵复杂度；用户手动选文件即可 |

## 3. 数据模型

`DB_VERSION` 由 1 提到 **2**，`applyMigrations` 增加这三张表（现有的 `createObjectStore` 只在表不存在时执行，所以迁移对老库是安全的、不需要搬数据）。

### 3.1 `invoices`（发票）

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `number` | 发票号码。**不强制校验格式**——增值税发票 8 位、全电发票 20 位，各地还有差异，硬校验只会挡住正确的票 |
| `issuedAt` | 开票日期（毫秒时间戳） |
| `amountCents` | 价税合计金额（整数分，与记账同一套口径） |
| `seller` | 销售方名称 |
| `type` | 发票类型，枚举见 3.4 |
| `buyerTitle` | 购买方抬头 |
| `buyerTaxId` | 购买方纳税人识别号 |
| `taxCents` | 税额（整数分，可空） |
| `note` | 备注 |
| `fileId` | 指向 `invoiceFiles`，可空（只记号码不存图也允许） |
| `txnId` | 挂靠的账目 id，可空 |
| `reimbursementId` | 所属报销单 id，可空 |
| `archived` | 仅存档标记——为真时不计入「待报销」统计 |
| `createdAt` | 录入时间 |

索引：`by_issuedAt`、`by_txn`、`by_reimbursement`、`by_number`（查重与跳转用）。

### 3.2 `invoiceFiles`（发票图片 / PDF）

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `blob` | 原图或 PDF 的二进制 |
| `thumbBlob` | 缩略图（PNG/JPEG）；PDF 没有缩略图，为 `null` |
| `mime` | MIME 类型 |
| `size` | 原图字节数（用于显示与备份体积预估） |
| `createdAt` | 存入时间 |

**为什么单独一张表**：列表页只需要缩略图。若把原图塞在发票记录里，打开列表就得把所有几 MB 的图读进内存——手机上会明显卡顿。分表后，详情页才按 `fileId` 去取原图。

### 3.3 `reimbursements`（报销单）

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `title` | 标题，默认「M月报销 · N 张」，可改 |
| `status` | `draft` 待提交 / `submitted` 已提交 / `settled` 已到账 |
| `createdAt` / `submittedAt` / `settledAt` | 三个时间点，后两个可空 |
| `accountId` | 到账账户，可空（到账时才需要） |
| `txnId` | 到账时生成的收入账 id，可空 |
| `note` | 备注 |

索引：`by_status`。

### 3.4 发票类型枚举

`vat_special` 增值税专用发票 / `vat_normal` 增值税普通发票 / `e_invoice` 电子发票 / `itinerary` 行程单 / `train` 火车票 / `taxi` 出租车票 / `other` 其他。

存在代码里作为常量（`app/invoice-model.js`），**不做可配置**——真需要「其他」就够了。

### 3.5 金额口径

全部用**整数分**，与 `app/money.js` 一致。税额也是分。发票金额与关联账目的金额**不做一致性校验**（一次出差 5 张票合计 3000，可能挂在多笔账上，也可能只挂一笔；强行校验只会拦人）。

## 4. 图片处理

### 4.1 两个入口

- **拍照**：`<input type="file" accept="image/*" capture="environment">`，直接唤起后置摄像头
- **选文件**：`<input type="file" accept="image/*,application/pdf">`

APK 里的选文件走的是壳已经实现好的 `onShowFileChooser`（账单导入时已打通并实测），不需要新增原生代码。

### 4.2 压缩

用 Canvas 手写，不引任何库：

| 参数 | 值 | 理由 |
|---|---|---|
| 长边上限 | 1600 px | 发票上的字要能看清，1600 足够；再大只是浪费体积 |
| JPEG 质量 | 0.72 | 实测这个质量下发票文字仍清晰，体积约为原图的 5~10% |
| 小于阈值不压 | 原图 < 300 KB 时直接用原图 | 避免「压完反而更大」 |
| 压完更大则放弃 | 压缩结果字节数 ≥ 原图时用原图 | 同上 |

手机拍的 3~5 MB → 通常落到 200~400 KB。

**PDF 不压缩**，原样存。

### 4.3 缩略图

另存一张长边 **240 px**、质量 0.7 的 JPEG（约 10~20 KB）。列表页只加载它。

### 4.4 失败的兜底

Canvas 压缩在极少数情况下会失败（超大图、内存不足、`createImageBitmap` 不可用）。失败时**回退存原图**，并在界面上提示「图片未能压缩，已按原样保存」——不能因为省体积就把用户的发票弄丢。

## 5. 挂靠与查重

### 5.1 挂靠（计划 4）

- 发票详情页有「关联到某笔账」，点开是一个账目选择器（按日期倒序，带搜索）
- 一笔账可以挂多张票；一张票最多挂一笔账（要换就改挂）
- 记账侧：流水详情里显示「已关联 N 张发票」，可点进去看
- **挂靠是可选的**，不挂的票在列表里标「未挂账」

### 5.2 发票号查重

录入时按 `number` 精确查重（先 `by_number` 索引查，命中就提示）：

> 「这张票已经录过了」+ 一张小卡显示已有那条的销售方/金额/日期 + 「去看看」按钮

**不做自动合并、不做自动覆盖**——两张同号票理论上不该存在，真出现（比如输错了）由人来决定怎么处理。

号码为空时不查重（允许只存图不填号码）。

## 6. 报销流程（计划 5）

### 6.1 状态机

```
（新建发票）→ 待报销 ──发起报销──→ 报销单.draft
                                      │
                                 提交给公司
                                      ↓
                              报销单.submitted
                                      │
                                   钱到账
                                      ↓
                              报销单.settled ──→ 可生成一笔收入账
```

发票的报销状态**不单独存**，由「有没有 `reimbursementId`」和「所属报销单的状态」推导出来。这样只有一处真相，不会出现「发票说已报销、报销单说还没提交」的矛盾。

**「仅存档」的票不进这条流水线**：`archived === true` 的发票不出现在「待报销」筛选里，也不能被选进报销单。它的作用是留底（保修、退换货），所以取消「仅存档」勾选就重新回到「待报销」。已经在报销单里的票若被勾成「仅存档」，先要求把它从报销单里移出——不允许一张票同时是「已提交待报销」和「仅存档」。

### 6.2 发起报销

在发票列表里多选（或从详情页逐张加），点「发起报销」→ 创建报销单（`draft`）→ 这些发票的 `reimbursementId` 指向它。

报销单详情页可以：改名、移除某张票（票回到「待报销」）、提交（`submitted`）、标记到账（`settled`）。

### 6.3 到账时自动入账

标记「已到账」时弹一个确认：

> 「这笔报销到账了，要记一笔收入吗？」
> 金额 **¥3,000.00**（自动填这批发票的合计，可改）
> 账户 **［选一个］**（默认取 `settings.lastAccountId`，与记账面板「上次用的账户」是同一个来源）
> 分类 **［退款 / 其他 / …］**（默认「退款」，可改）

确认后：
- 生成一笔 `kind: 'income'` 的交易，带 `source: 'reimbursement'` 和 `reimbursementId`
- 报销单记下 `txnId`
- 不确认也能标记到账（有些人报销款和记账分开管）

**删除保护**：删掉报销单时，若它已经生成过收入账，先问「那笔收入要不要一起删？」——两边都留会变成对不上的账。

### 6.4 「到账」金额与发票合计不一致时

公司少报、扣税、抹零都可能发生。到账确认框里的金额**可以改**，与发票合计的差额在报销单详情里显示一行「差额 −¥12.00」。不为了对齐而阻止用户。

## 7. 界面

### 7.1 导航

底部四个 Tab：**记账 / 发票 / 统计 / 密码箱**。`app/router.js` 的 `TABS` 增加一项，图标沿用现有三个 Tab 的 emoji 风格（🧾），遵循既有模式而不是引入一套新写法。

### 7.2 发票列表（发票 Tab 首页）

- 顶部：搜索框 + 筛选切换（全部 / 待报销 / 已报销 / 未挂账 / 仅存档）
- 汇总条：本月发票合计、待报销合计
- 列表项：缩略图（PDF 显示图标）+ 销售方 + 金额 + 日期 + 状态标签
- 右下角悬浮「+」新建
- 空状态：一句引导 + 直接拍照的按钮

### 7.3 发票编辑（新建 / 修改）

半屏 sheet，字段顺序即录入顺序：图片区（点击选择/拍摄）→ 号码 → 日期 → 金额 → 销售方 → 类型 → 抬头 → 税号 → 税额 → 备注 → 关联账目 → 保存。

金额用项目现有的 `createKeypad` 数字键盘（与记账一致，不自造一套）。

### 7.4 发票详情

原图（点击全屏、可双指缩放）→ 字段列表 → 关联的账目 / 报销单 → 编辑 / 删除。

### 7.5 报销单（计划 5）

列表页按状态分组；详情页显示票的缩略图列表、合计、时间线（创建/提交/到账）、操作按钮。

### 7.6 记账侧

流水详情里加一行「发票（N）」，点击进入发票列表并过滤到这笔账的票。

## 8. 备份与恢复

### 8.1 备份内容

`buildBackup` 的 `data` 增加 `invoices`、`invoiceFiles`、`reimbursements` 三个数组。

图片以 **base64 字符串**放进 `invoiceFiles[].blob` / `.thumbBlob`（零依赖下打不了 zip，只能这样）。

### 8.2 体积与选项

导出前先算一遍：显示「含 N 张发票图片，预计约 X MB」，并给两个按钮：

- **含图片导出**（默认）
- **不含图片导出** —— 只备份账目与发票字段，图片位留空；恢复后发票记录还在、图需重新补

### 8.3 恢复

- base64 反解回 Blob 存进 `invoiceFiles`
- **老备份兼容**：没有这三个字段的备份照常导入，三张表清空即可
- 恢复前仍沿用现有的二次确认与「会覆盖本机数据」提示

### 8.4 向下兼容的边界

备份格式版本号仍为 1（加字段不改版本）。若用户拿 v2 的备份去恢复 v1 的应用，多的字段会被 `validateBackup` 忽略——**这是已知且接受的**，因为只有一个用户、一台设备，不存在跨版本回退的真实场景。

## 10. 计划划分

**计划 4 · 发票本体**（做完就能用）：schema 迁移 → `invoice-model.js` → `image-scale.js` → 图片存取（压缩/缩略图）→ `invoice-store.js`（CRUD/查重/挂靠）→ 列表 → 编辑器 → 第 4 个 Tab 与路由 → 记账侧「N 张发票」→ 备份恢复接入 → 收尾（SW/文档/清单）。

**计划 5 · 报销流程**：`reimburse-model.js`（状态机）→ `reimburse-store.js` → 报销单界面 → 到账自动入账 → 发票侧接入报销状态 → 备份恢复与文档。

每个计划完成时都要：全量测试绿、SW 的 `CACHE` 版本 +1 并补 `ASSETS`、更新手动验证清单、在模拟器上至少实测一遍主流程。

## 11. 风险与取舍

| 风险 | 处理 |
|---|---|
| 含图备份过大导致导出/导入卡死或崩溃 | 默认提示体积并给「不含图片」选项；导出前先算，不先算就导出等于让用户蒙在鼓里 |
| 图片压缩让发票字看不清 | 1600 px / 0.72 是保守值；且压缩失败或变大时一律回退原图 |
| 发票号查重挡住正常录入 | 只提示不阻止，允许「仍然保存」 |
| 分表后备份要拼装两个数组，容易漏 | 写一条探针：存入带图发票 → 导出 → 清库 → 导入 → 图片字节数与缩略图都一致 |
| 老库升级到 DB_VERSION 2 出问题 | 迁移只做 `createObjectStore`（表不存在才建），不碰老数据；探针里专门测「用 v1 建库并塞入记账数据 → 升到 v2 → 数据完好」 |
| PWA 与 APK 两边的选文件行为不同 | 两侧都实测；APK 侧已有 `onShowFileChooser` 打底 |
